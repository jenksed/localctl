# LocalCTL v0.4 — Know the Territory

> Turn experiment evidence into bounded, deterministic capability intelligence without turning evidence into authority.

v0.3 answered:

> What happened when this exact local model ran this exact experiment on this machine?

v0.4 answers the next question:

> Given the evidence LocalCTL has actually collected, what capability appears supported now, how strong and fresh is that support, which installed model currently has the strongest evidence for a workload, and what should be tested again?

That sounds like a small step. It is the step where a pile of observations begins to become an operating map.

---

## 1. The intelligence ladder

LocalCTL keeps four different kinds of claims separate:

```text
OBSERVATION
  exact run evidence
  schema v3
      │
      ▼
DERIVED CAPABILITY INTELLIGENCE
  deterministic rules v1
  source run IDs preserved
      │
      ▼
ADVISORY RECOMMENDATION
  evidence-relative comparison
  no execution authority
      │
      ▼
FUTURE ANALYST LAYER
  explanations / synthesis / questions
  separately attributed AI analysis
```

The critical invariants are:

```text
observation != derived intelligence

derived intelligence != qualification

recommendation != authority

AI interpretation != deterministic capability state
```

v0.4 implements the middle two deterministic layers. It does not implement the future analyst.

---

## 2. Public v0.4 commands

### `localctl capability <model>`

Derives a current capability map for one model and profile.

```bash
localctl capability granite
localctl capability granite --profile=fast
localctl capability granite --json
```

Human output shows:

- model and artifact identity
- profile
- machine identity
- candidate roles supported by current evidence
- pack-level state
- evidence strength
- freshness
- auto-scored pass rate
- deterministic exercise coverage
- comparable run count

A capability invocation also persists the derived map under:

```text
~/.localctl/intelligence/capability/YYYY/MM/DD/
```

The saved snapshot contains the rule version and exact source run IDs behind every pack assessment.

### `localctl matrix`

Projects the installed model fleet into one compact evidence map.

```bash
localctl matrix
localctl matrix --profile=fast
```

It is intentionally not a universal leaderboard. The cells mean “what does the current bounded local evidence support for this exact profile?”

### `localctl recommend <pack>`

Ranks installed models for one versioned workload pack.

```bash
localctl recommend developer-core
localctl recommend linux-investigation
localctl recommend structured-output --profile=fast
localctl recommend reasoning-analysis --json
```

The command can name an **evidence leader** only when a model reaches `SUPPORTED` or `STRONG` under the current rules. Otherwise it says no installed model has enough support yet and points to the next experiment.

This is advisory decision support. LocalCTL does not automatically route work to the winner.

### `localctl requalify <model>`

Creates a deterministic refresh plan from freshness and evidence gaps.

```bash
localctl requalify granite
```

By default it is plan-only.

```bash
localctl requalify granite --run
```

`--run` executes only the single highest-priority pack from the displayed plan. It does not create an autonomous background qualification loop.

### `localctl intelligence list|show|audit`

Inspects the derived-intelligence layer itself.

```bash
localctl intelligence list
localctl intelligence show cap_...
localctl intelligence audit
```

`audit` checks that capability snapshots retain their rule identity and that each claimed source run still resolves to durable observation evidence.

## 3. The comparability boundary

A historical run contributes to a v0.4 capability assessment only when it satisfies the current deterministic comparison boundary.

Required:

1. evidence schema v3 or later
2. canonical input — private real-work evidence is excluded from canonical capability promotion
3. exact capability pack ID
4. exact pack version
5. exact profile ID
6. comparable machine fingerprint
7. exact installed artifact SHA-256 when an artifact hash is available

Anything outside that boundary is not silently averaged in. It is counted as excluded evidence.

This matters because these are not equivalent claims:

```text
Granite passed this task once.

Granite passed this task under the current profile.

This exact Granite GGUF passed the current version of this capability pack
on this machine under this profile.
```

v0.4 is designed to reason from the third kind of claim.

---

## 4. Machine comparability

The v1 rule considers two machine fingerprints comparable when:

- OS is present and equal
- architecture is present and equal
- chip matches when both observations report a chip
- memory size matches when both observations report memory

Missing machine identity is not promoted as comparable evidence.

This is intentionally conservative. Later versions may introduce explicit machine classes, but v0.4 does not infer equivalence across hardware families.

---

## 5. Artifact identity

When the requested model is currently installed and its GGUF digest is available, the capability map binds comparable evidence to that SHA-256.

A filename match is not enough.

```text
same display name != same artifact
```

Historical reporting can still find removed models. But current capability promotion is strongest when the installed artifact can be bound to the source observations by content identity.

---

## 6. Evidence strength

Evidence strength and capability state are separate dimensions.

Strength asks:

> How much comparable deterministic evidence do we have?

v0.4 rule version `v1` uses:

| Strength | Deterministic interpretation |
| --- | --- |
| `NONE` | no scored comparable evidence |
| `HUMAN_ONLY` | manual evidence exists but no deterministic score |
| `EARLY` | fewer than 3 scored runs or <25% deterministic exercise coverage |
| `DEVELOPING` | fewer than 8 scored runs or <60% deterministic coverage |
| `SUPPORTED` | enough coverage/runs to move beyond developing evidence |
| `STRONG` | >=90% deterministic exercise coverage across at least 2 experiments |

These are LocalCTL evidence labels. They are not statistical confidence intervals and are not claims about the model outside the tested pack.

---

## 7. Freshness

Freshness asks:

> How old is the newest comparable evidence behind this capability claim?

The initial v1 policy is deliberately simple and visible:

| Freshness | Latest comparable evidence |
| --- | --- |
| `CURRENT` | 0–14 days old |
| `AGING` | 15–45 days old |
| `STALE` | >45 days old |
| `UNKNOWN` | no comparable evidence |

These thresholds are a versioned operational heuristic, not a universal law.

The important improvement is that freshness is now explicit, testable, and revisable. A model does not remain “good at Kubernetes” forever because it passed something months ago under a different artifact or profile.

---

## 8. Capability state

State asks:

> Given the amount, outcome, runtime reliability, and freshness of comparable evidence, what can LocalCTL responsibly say now?

The v1 state derivation is deterministic:

1. no comparable evidence → `UNKNOWN`
2. stale newest evidence → `STALE`
3. only manual evidence → `REVIEW_REQUIRED`
4. inference success rate <80% → `RUNTIME_UNRELIABLE`
5. deterministic pass rate <60% → `WEAK`
6. deterministic pass rate 60–84.99% → `MIXED`
7. >=95% pass rate + `STRONG` evidence + `CURRENT` freshness → `STRONG`
8. evidence strength `SUPPORTED` or `STRONG` → `SUPPORTED`
9. otherwise → `PROMISING`

This is not a hidden weighted score. The rule order is inspectable in source and identified by `rule_version: v1` in persisted snapshots.

---

## 9. Candidate roles

v0.4 can surface a model as a **candidate** for a role only when the related pack is currently `SUPPORTED` or `STRONG` and is not stale.

Current mapping:

| Pack | Candidate role |
| --- | --- |
| `developer-core` | developer helper |
| `linux-investigation` | Linux investigator |
| `docker-investigation` | Docker investigator |
| `kubernetes-investigation` | Kubernetes investigator |
| `writing-summarization` | technical writing helper |
| `structured-output` | structured-output worker |
| `reasoning-analysis` | bounded reasoning helper |

“Candidate role” is intentionally weaker than “safe autonomous agent role.”

A local model can be useful without being authorized to mutate anything.

---

## 10. Recommendation semantics

`localctl recommend <pack>` compares installed models only.

It uses a deterministic lexicographic ordering rather than a single magic score:

1. capability state
2. evidence strength
3. pass rate
4. deterministic coverage
5. model name as a stable tie-breaker

State ordering is:

```text
STRONG
SUPPORTED
PROMISING
MIXED
WEAK
RUNTIME_UNRELIABLE
REVIEW_REQUIRED
STALE
UNKNOWN
```

A recommendation therefore means:

> Among the installed models LocalCTL can compare for this exact pack/profile/machine/artifact boundary, this model currently has the strongest bounded evidence.

It does **not** mean:

- best model in the world
- best model on every prompt
- cheaper than every cloud model
- production qualified
- authorized to execute a task

---

## 11. Why private work is excluded from canonical promotion

v0.3 added private real-work runs because transfer to actual work matters.

But private data has uncontrolled content. Two PR diffs or two incident logs are not automatically comparable benchmark cases.

Therefore:

```text
private work -> durable evidence + human judgment
private work -X-> canonical capability promotion
```

A later LocalCTL version may use separately modeled real-work evidence, but v0.4 refuses to quietly mix it with canonical pack scores.

## 12. Derived intelligence provenance

Capability intelligence is persisted separately from raw observations.

```text
~/.localctl/
├── runs/
│   └── .../observation.json
└── intelligence/
    └── capability/
        └── YYYY/MM/DD/
            └── cap_<timestamp>_<model>_<profile>.json
```

A capability snapshot includes:

- capability snapshot schema version
- capability rule version
- generation timestamp
- model identity
- artifact SHA when available
- profile
- machine fingerprint
- candidate roles
- pack assessments
- exact `source_run_ids` for each assessment

The source observations remain untouched.

This is the key provenance relationship:

```text
capability claim
    │
    ├── rule_version: v1
    │
    └── source_run_ids[]
            │
            ▼
      immutable observations
```

If the rule changes later, LocalCTL can derive a new snapshot without pretending the old observation changed.

---

## 13. Intelligence audit

`localctl intelligence audit` verifies the derived layer.

It checks:

- snapshot schema is recognized
- `rule_version` exists
- `comparable_runs` equals the number of recorded source run IDs
- each source run ID still resolves to an observation

The audit does not prove the model is good. It proves the derivation retains a traceable evidence chain.

---

## 14. Requalification

Requalification converts freshness and weak coverage into a bounded next-test plan.

Initial priority order:

1. stale evidence
2. unknown capability
3. runtime-unreliable evidence
4. weak evidence
5. mixed evidence
6. manual-review-required evidence
7. promising but under-supported evidence
8. aging supported evidence
9. aging strong evidence

Current supported evidence does not get retested merely to create more numbers.

The default command prints the plan only. `--run` executes one top-priority pack.

This protects the learning loop from turning into an uncontrolled benchmark treadmill.

---

## 15. What v0.4 still does not know

v0.4 does not yet prove:

- task-specific cost equivalence against paid frontier APIs
- peak unified-memory demand across every context size
- semantic quality for open-ended work without human judgment
- correctness of generated code through sandboxed compilation/tests
- safety of model-proposed commands or patches
- generalization to unseen domains
- optimal routing policy
- whether an AI analyst would agree with the deterministic state

Those gaps are features of the truth model, not omissions to hide.

## 16. v0.3 → v0.4 → v0.5

```text
v0.3  FIND THE EDGES
      durable experiments
      exact machine/model/runtime/config evidence
      repeatability
      canonical vs private input
             │
             ▼
v0.4  KNOW THE TERRITORY
      deterministic capability state
      evidence strength
      freshness
      candidate roles
      advisory recommendations
      requalification
      derivation provenance
             │
             ▼
v0.5  ANALYZE THE TERRITORY  (future)
      bounded AI explanation
      evidence synthesis
      comparative questions
      uncertainty narration
      operator-facing analyst workflows
```

The v0.5 seam is deliberate.

An AI analyst may eventually explain or challenge the deterministic capability map. It must not silently become the source of the map.

---

## 17. The release invariant

A useful local model system should be able to answer all of these without hand-waving:

```text
What exactly ran?
What exactly happened?
What evidence supports this capability claim?
How old is that evidence?
Which evidence was excluded, and why?
Which local model currently has the strongest bounded support for this workload?
What should I test next?
Who is actually allowed to execute the work?
```

v0.4 moves LocalCTL through the first seven questions.

The eighth remains a separate authority problem on purpose.
