# LocalCTL v0.5 — Learn What Matters Next

v0.4 asks: **what does the evidence already collected on this exact machine support now?**

The first v0.5 slice asks: **given what this machine already knows, what is worth learning next — including models that appeared after the last lab session?**

This is the deterministic foundation for the later v0.5 intelligence plane. It does not yet add an LLM analyst, embedding memory, reranker, automatic downloads, or automatic routing.

## The loop

```text
LOCAL EVIDENCE                         EXTERNAL ECOSYSTEM
capability gaps                        Hugging Face metadata
stale evidence                         recent GGUFs
        │                                      │
        └──────────────────┬───────────────────┘
                           ▼
                   OPPORTUNITY ENGINE
                           │
                           ▼
                what is worth testing?
                           │
                           ▼
                    OPERATOR CHOOSES
                           │
                           ▼
                       LAB RUN
                           │
                           ▼
                    LOCAL EVIDENCE
```

The external side may create questions. It may not answer them.

```text
Hugging Face metadata != local capability evidence
candidate != compatible
compatible != useful
popular != good
new != better
selected for audit != recommended
```

## `localctl next`

```bash
localctl next
localctl next --limit=10
localctl next --profile=fast
localctl next --offline
localctl next --json
```

`next` combines two bounded sources:

1. local evidence opportunities derived from the v0.4 capability map and deterministic requalification rules;
2. ecosystem candidates from live Hugging Face GGUF metadata filtered through saved Model Radar criteria.

Local evidence refreshes occupy the higher priority band. Ecosystem metadata can make a model worth testing, but cannot make it a recommendation.

If Hugging Face is unavailable, `next` continues with local evidence. `--offline` never performs the live radar request.

## Model Radar

```bash
localctl radar
localctl radar scan --json
```

Every external result remains:

```text
local_status: UNTESTED_LOCAL
```

There is deliberately no `SUPPORTED`, `STRONG`, or `RECOMMENDED` state for a model that has never produced evidence on this machine.

## Criteria

Show criteria:

```bash
localctl radar criteria
```

Change only what matters:

```bash
localctl radar criteria set --fit=comfortable --use=coding,debugging,review
```

A stricter example:

```bash
localctl radar criteria set \
  --fit=comfortable \
  --use=coding,review \
  --release-days=30 \
  --min-downloads=100 \
  --license=permissive
```

Reset:

```bash
localctl radar criteria reset
```

Criteria are stored at `~/.localctl/radar.json`. This is operator preference/state, not evidence.

### Fit

Initial fit modes:

```text
comfortable
stretch
any
```

Without an explicit `--max-params`, LocalCTL derives a conservative parameter-size screen from system memory. The first rule reserves substantial memory for the OS, editor, KV cache, and runtime overhead and uses a Q4-class estimate:

```text
comfortable -> 55% memory budget
stretch     -> 72% memory budget
any         -> no automatic parameter cap
```

This is a discovery screen, not runtime-fit evidence. It does not prove that a quant exists, the GGUF loads, useful context fits, Metal behaves well, speed is acceptable, or the model is useful.

When fit screening is active and LocalCTL cannot determine a parameter-size class, the candidate is excluded. `fit=any` opts into candidates the screen cannot classify.

### Use signals

`--use=coding,debugging,review` influences candidate ordering from repository IDs/tags. Those metadata are too weak to become capability evidence.

Embedding and reranking specialists are excluded from the default general-model feed unless explicitly requested:

```bash
localctl radar criteria set --use=embedding
localctl radar criteria set --use=reranking
```

This is the seam for later semantic-memory and reranking work.

### License metadata

Initial filters:

```text
any
known-commercial
permissive
```

Restrictive filters require recognized Hugging Face license metadata. This is a discovery convenience, not a license audit or legal advice; the actual model license still needs verification.

## Candidate lifecycle

```text
RADAR DISCOVERY
  external metadata only
        │
        │ localctl explore select <owner/model-GGUF>
        ▼
AUDIT QUEUE
  explicit operator interest
        │
        │ install with preferred model manager
        ▼
INSTALLED MODEL
        │
        │ audition / pack / verify / head-to-head
        ▼
LOCAL EVIDENCE
        │
        ▼
CAPABILITY MAP
        │
        ▼
ADVISORY RECOMMENDATION
```

The radar does not download models automatically. Selection remains operator intent, not qualification.

## Opportunity ordering is not a model-quality score

The feed needs deterministic ordering. Local opportunities use v0.4 requalification priority. Ecosystem candidates use a lower bounded band informed by requested-use metadata matches, recency, and comfortable machine screening. Downloads are only a tie-break signal inside radar ordering.

The number orders questions. It does not grade models.

## GUI seam

The machine-readable surfaces are first-class:

```bash
localctl radar scan --json
localctl next --json
```

They expose structured machine, criteria, candidate, opportunity, status, source, and next-action data. A future Wails/TypeScript GUI can call the same Go application layer directly; it should not parse terminal prose or invent another truth model.

## Explicit non-goals of this slice

Not implemented here:

- embedded semantic memory;
- reranker lifecycle management;
- local LLM analysis of experiment history;
- AI-generated findings;
- automatic experiment-plan generation by an LLM;
- automatic downloads/deletion/replacement;
- routing real work to newly discovered models;
- claims that parameter count proves runtime fit;
- claims that ecosystem metadata proves workload capability.

Those are subsequent v0.5 seams built on top of this contract.
